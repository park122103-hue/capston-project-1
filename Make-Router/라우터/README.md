initial_mapping.cpp도 거의 문제 없긴 하지만, 수정 예정인 Glist와 grid를 사용하기 때문에 조금 조심할 필요가 있습니다. (사실상 문제 없긴 함. 저한테 물어보면 바로 알려드릴게요.)  
  
## Files  
|File|Description|
|---|-----|
|main.cpp|메인함수. 테스트할 양자 회로와 물리 노드 간선이 하드코딩 되어있다. 이니셜 매핑으로 객체의 매핑 배열을 완성 시킨 뒤 라우팅을 한다. 아직 로직이 미완성인 상태이므로(심지어 control qubit과 target qubit 구분도 안되어 있음) 가져다 쓴다면 제게 먼저 코딩 의도를 물어봐주기를 바랍니다.|
|QCompiler.h|컴파일에 관한 각종 함수들과, 매핑, 라우팅 전반에 대한 클래스를 정의한 헤더. 크게 전처리를 위한 set 계열 함수, 매핑을 위한 mapping 계열 함수, 그리고 라우팅을 위한 routing 계열 함수로 나눌 수 있다.<br>memo.main.cpp에서 말했듯이 제어 큐비트와 타겟 큐비트가 구분이 안된다. 그를 구분하기 위해서 Glist와 grid에 other을 없애고, id만 기입한 뒤 헤더에서 qc를 저장하는 방법이 있다. 아마 이렇게 바꾸게 될 것 같음.|
|data_preprocessing.cpp|클래스의 생성자와 set 계열 함수들을 구현한 코드. 물리 노드 간선 리스트를 받아 인접 노드 리스트(adj)와 거리 행렬(dist)로 바꾸는 함수, 그리고 양자 게이트 리스트를 받아 Glist와 grid(버블그리드)로 바꾸는 함수가 구현되어 있다. 또한 약간의 시간 복잡도 이득을 위하여 중심도(Centrality)와 중요도(Importance)를 선계산하여 배열에 저장해두는 로직도 구현되어 있다.|
|initial_mapping.cpp|이니셜 매핑을 구현한 코드.|
|routing.cpp|라우팅을 구현한 코드. 비용을 줄이는 방향으로 스왑을 하게 되는데, 이는 사실 상호작용 하고자 하는 두 큐비트간의 거리를 줄이는 방향이라는 보장이 없다(지금 당장 처리할 큐비트는 비용이 높게 책정되므로 확률은 좀 높겠지만). 따라서 무한히 핑퐁할 수도 있다. 그러한 문제가 있는 코드이다. 절대 가져다 쓰지 말 것!<br>memo.해결할만한 아이디어는 무조건 거리가 줄어드는 쪽으로 움직인다? 하지만 그건 사실상 t=0인 게이트들에 가중치를 높게 주는 것과 다르지 않음. 그리고 교수님거랑 완전 똑닮음. 일단 내 첫 번째 아이디어는 일단 비용 낮은 곳으로 가다가 좀 아닌 것 같으면 롤백 해서 거리 줄어드는 쪽으로 가기. 그런데 이렇게 하면 이로 인해서 또 다른 큐비트가 무한 핑퐁에 빠질 수도 있기 때문에 구현이 참 난감하다. 휴리스틱 타이브레이킹이 도배될지도 몰라. 두 번째 아이디어는 지수 감쇠(alpha)가 아닌 다른 함수(f(t)) 사용하기. 하지만 이것도 난감 한 것이, f(t)가 t=0일 때의 함수값이 t!=0일 때의 함수값들의 합이 더 커야 하는가? 그렇게 된다면 일단 교수님의 아이디어와 닮았지만 조금 다른 재밌는 함수가 나오기는 한다. 하지만 별로 유용하지 않을 것 같긴 하다.<br>memo.재밌는 얘기 하나 더. 불확정성으로 인해 매 깊이 alpha만큼 감쇠된다고 하자. 그러면 swap 성적도 alpha만큼 줄어들까? swap은 사실 1%의 불확정성도 치명적이여서 막 100%의 오버헤드가 치솟는게 아닐까?|
